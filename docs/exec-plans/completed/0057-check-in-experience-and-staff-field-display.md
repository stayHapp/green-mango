# 签到体验与工作人员字段显示优化

## 任务名称

优化嘉宾签到状态刷新、工作人员端字段显示和重复扫码提示。

## 背景

当前项目已经切换到 PostgreSQL 并完成三端 MVP 主链路验证。现场签到体验还存在三个需要收口的问题：工作人员扫码后嘉宾端状态需要更及时刷新；后台未启用座位号时工作人员端仍可能展示座位信息；重复扫码只返回固定错误提示，无法向工作人员说明已签到嘉宾、签到时间、方式和操作人员。

## 用户确认状态

用户已明确要求“先实现 0057 方案”，并指定嘉宾端轮询时间为 3 秒。允许在本计划范围内修改前后端代码、测试和文档，并运行本地验证。

## 目标

- 嘉宾端未签到时每 3 秒刷新当前签到状态，页面不可见时暂停，恢复可见或聚焦时立即刷新。
- 嘉宾端一旦检测到已签到，停止轮询并展示签到时间。
- 工作人员端嘉宾信息按后台字段启用状态显示；座位号未启用时不展示座位信息，启用且有值时展示。
- 重复扫码或重复手工签到时，工作人员端展示结构化提示，包括嘉宾姓名、签到时间、签到方式和操作人员。
- 首次签到、重复签到和无效二维码提示有明显区分。

## 不在本次范围内的内容

- 不实现同一会议多天/多场次签到模型。
- 不引入 WebSocket、SSE 或长轮询。
- 不修改会议服务是否必须登录的访问权限。
- 不新增撤销签到、补签、离线签到或多签到点。

## 技术决策与待确认项

- 嘉宾端轮询间隔固定为 3 秒，按用户要求执行。
- 本次保留“一个嘉宾在一个会议中只签到一次”的既有数据库模型。
- 重复签到继续使用 `409 Conflict`，但后端返回结构化 `detail`，前端按 `code=already_checked_in` 展示黄色提示。
- 工作人员端字段显隐优先使用后端返回的字段 key 列表，避免前端硬编码后台配置。
- 当前无待确认项。

## 分步计划

1. 补充后端重复签到结构化响应和工作人员嘉宾字段显隐数据。
2. 更新前端 API 类型和错误解析，区分重复签到、无效二维码和其他错误。
3. 实现嘉宾端 3 秒签到状态轮询和页面可见性控制。
4. 实现工作人员端按字段配置展示嘉宾信息，并优化重复扫码/手工签到提示。

7. 运行后端测试、前端构建、格式检查和浏览器三端流程验证。

## 验收标准

- 工作人员扫码后，嘉宾端在最多约 3 秒内从未签到更新为已签到。
- 嘉宾端页面不可见时不持续轮询，恢复可见或聚焦时立即刷新。
- 后台未启用座位号时，工作人员端不展示座位号；启用且有值时正常展示。
- 第二次扫描同一嘉宾二维码时，展示已签到嘉宾、签到时间、签到方式和操作人员。
- 首次签到成功、重复签到、无效二维码三种提示样式和文案明显区分。
- 后端测试、前端构建、`git diff --check` 和浏览器验证通过。

## 验证方式

- `backend/.venv/bin/pytest -q`
- `cd frontend && npm run build`
- `git diff --check`
- 浏览器验证嘉宾端未签到页、工作人员扫码签到和嘉宾端 3 秒状态刷新。
- API 冒烟验证管理员、嘉宾、工作人员和签到统计闭环。

## 风险与注意事项

- 3 秒轮询在 100 人规模压力可接受，但应只在未签到且页面可见时进行。
- 重复签到结构化 detail 需要兼容既有 `getApiErrorMessage` 字符串错误处理。
- 工作人员端字段显隐不能影响后端权限判断，只改变现场展示信息。
- 本任务不改变数据库唯一约束。
