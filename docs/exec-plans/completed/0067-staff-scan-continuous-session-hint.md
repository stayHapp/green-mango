# 工作人员端连续扫码与场次提示优化

## 任务名称

优化工作人员端扫码签到体验和当前签到场次提示。

## 背景

工作人员端当前已经按后端“当前有效场次”写入签到记录，但页面没有明确展示当前签到场次。扫码页仍使用“开启摄像头”按钮，识别到一次二维码后自动关闭摄像头，不适合现场连续扫码。用户确认按效果图布局优化：点击扫码区域开启摄像头，开启后在扫码区域右上角显示关闭按钮，结果区在一个屏幕内可见。

## 用户确认状态

用户已确认按照效果图布局格式进行优化。

## 目标

1. 工作人员端明确展示当前签到场次。
2. 当前场次在没有签到记录时也能可靠显示。
3. 扫码区域点击即可开启摄像头。
4. 摄像头开启后持续扫码，只有点击关闭按钮或离开扫码页才关闭摄像头。
5. 识别成功后展示紧凑结果卡片，并显示签到场次。
6. 连续扫码时加入冷却逻辑，避免同一个二维码连续重复提交。
7. 去掉“开启摄像头”按钮和扫码说明文案。

## 不在本次范围内的内容

- 不修改后台签到管理规则。
- 不实现声音、震动或外接扫码枪。
- 不实现离线扫码。
- 不做浏览器安全策略绕过验证。

## 技术决策与待确认项

- 新增工作人员端当前签到场次只读接口，直接复用后端当前有效场次服务。
- 前端在加载工作台时并行读取会议、嘉宾、签到记录和当前签到场次。
- 连续扫码保留摄像头开启状态，识别后继续扫描。
- 使用 token 与时间窗口做前端冷却，降低同一二维码重复提交。

## 分步计划

1. 新增工作人员端当前签到场次响应结构和接口。
2. 前端 API 增加当前签到场次读取。
3. 工作人员端页面增加当前签到场次提示。
4. 改造扫码区域点击开启、右上角关闭和持续扫描逻辑。
5. 优化扫码结果卡片，显示签到场次并保持紧凑。

## 验收标准

- 工作人员端扫码页可看到当前签到场次。
- 点击扫码区域可开启摄像头。
- 开启后不显示“开启摄像头”按钮，不显示“将嘉宾出示的二维码对准扫描框”提示。
- 开启后扫码区域右上角显示关闭按钮。
- 扫码成功后摄像头继续运行。
- 签到结果卡片展示签到场次。
- 后端测试和前端构建通过。

## 风险与注意事项

- 浏览器摄像头权限和真机行为无法通过构建验证完全覆盖。
- 连续扫码需要前端冷却，避免同一二维码在画面内多次提交。
- 新增后端接口后，本地需要重启后端。
